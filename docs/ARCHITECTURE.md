# 技术方案与决策

状态：M2 已接入本地存储与日记管理；v1 容器及密码模式已确定。日期：2026-11-10。

## M2 本地写作

`DiaryCore` 包含版本化容器、元数据、文件 codec、actor repository 与原子 writer；`DiaryState` 负责防抖保存、写入序列、会话和导航；`DiaryEditing` 为应用及原生探针提供相同的编辑器适配。UI 不直接编码或写日记文件。

普通库、独立示例库和临时验证库隔离。启动重建元数据列表，只加载当前正文；标题保留可见，私密内容以互斥的加密载荷保存。350 毫秒防抖保存会追赶写入期间的新增编辑；写入失败保留草稿并停止导航或关闭。细节与限制见 [DATA_FORMAT.md](DATA_FORMAT.md)。

本轮修复了原生撤销路径只改变 NSTextView、未更新绑定的情况：通过所属 UndoManager 的通知调用公共文本委托进行同步，避免自动保存拿到旧正文；未修改上游源码。

### 0.4 侧栏与私密会话边界

千篇库的启动调用栈定位到 SwiftUI OutlineList 更新中的 AppKit 行高缓存递归，固定行高仍可复现。侧栏改用 `ScrollView` + `LazyVStack`，保留日期分组、原生按钮、选中状态、完整辅助功能标题和上下键导航；移除触发警告的表格更新路径。详情编辑器与存储接口保持独立。

`DiaryPasswordPrompt` 将密码验证、错误、取消及会话身份检查放在可测试的 State 层；界面不根据变化中的全局锁定态临时改变请求模式。`DiaryEditorView` 的写回携带编辑器身份；过期回调被拒绝。

`ClearingEditorHost` 管理原生编辑子树生命周期。移除时撤销委托、清空正文和撤销记录、丢弃组合输入并释放 rootView；不使用上游 parking。锁定事件同时关闭密码面板。原生保留引用测试、窗口探针与外部辅助功能检查的范围见 [SECURITY_VALIDATION.md](SECURITY_VALIDATION.md)，不声称物理内存擦除或真实系统锁屏已经完成验收。

### WRITE-002 日记管理

`DiaryFilter` 只依赖元数据；标题搜索与自然日筛选组合，不引入数据库或正文索引。UI 按日期分组，筛选时保留当前编辑内容。切换日记列表与废纸篓前 flush 并清除当前会话。

废纸篓由库内 `Trash` 子目录表示，文件格式保持 v1。repository 在库写锁下验证 revision，以排他原子移动保留完整文件；恢复拒绝覆盖同 ID 文件。UI 不能绕过存储层直接搬动文件，也不提供隐含永久删除。

导出由 App 层的系统保存面板、State 层的解锁与保存检查、Core 层的 UTF-8 新文件写入组成。不会使用 `FileDocument` / 临时解密文件中转；只在用户确认目的地后访问会话正文。为避免明文中间文件和误覆盖，导出只创建新的 `.md`，与容器的临时文件原子替换分别处理。测试证据见 [WRITE002_VALIDATION.md](WRITE002_VALIDATION.md)。

## M1 落地（历史）

SwiftPM 工程分为 `DiaryCore`、`DiaryPlatform`、`DiaryApp` 和开发验证 CLI `DiaryProbe`。界面使用原生 MarkdownEngine 核心产品，固定到调研提交；参考项目的其他模块未复制。

加密核心已实现 AES-256-GCM 与每篇随机密钥，采用 PBKDF2-HMAC-SHA256 600,000 次和随机 salt 封装数据密钥；算法、版本、日记 ID 与 KDF 参数纳入认证附加数据。13 项核心测试及合成文件跨进程密码恢复已通过。容器当前仅处理 Markdown 载荷，完整日记元数据、版本迁移与持久化仍待 M2。

平台层已实现受指纹约束的 Keychain 访问与目录授权书签；CLI 受保护 Keychain 写入在本机返回 `errSecMissingEntitlement (-34018)`，尚未证明指纹认证成功。目录书签的 3 项测试、临时目录与真实 iCloud 路径的跨进程读写验证通过；真实 iCloud 上传被配额阻断，见下文备份小节。

具体证据与未完成项见 [M1_VALIDATION.md](M1_VALIDATION.md)。

## 总体方案

采用一个原生 macOS 应用进程：SwiftUI 管理窗口与列表，AppKit / TextKit 处理需要成熟文本行为的编辑器。系统框架负责加密、Keychain、Touch ID、定位与地图；天气使用按需网络请求；本地文件是日记主副本。

按编辑、文件、安全、位置天气、备份划分代码职责即可，不提前建立复杂框架。地图只在选点时创建；天气和备份不持续轮询。

## 编辑器选型

优先验证 SwiftMarkdownEngine 核心产品能否实现原生即时样式，并满足中文输入法、Markdown 保真和内存目标。它尚处 pre-1.0，必须固定版本。

如不满足需求，比较 AppKit 编辑区配原生阅读/预览组件的方案；Textual 需要 macOS 15，MarkdownUI 处于维护模式，不能跳过取舍直接加入。WebKit 预览仅作为有实际必要时再评估的替代，需计入所有相关进程内存。

最终结果由 `ED-001`、`ED-002` 的记录决定。不能用简单行内粗体演示代替完整 Markdown 即时预览验收。

## 数据模型建议

每篇日记使用一个独立、带版本的容器文件和 UUID，避免日记正文与元数据分开写导致不一致。正文内部保留 Markdown，可按需导出 `.md`；不保证容器本身能被任意 Markdown 编辑器直接编辑。

| 层 | 建议字段 / 内容 |
| --- | --- |
| 公开文件头 | schemaVersion、id、title、日记日期、时区标识、createdAt、updatedAt、加密状态 |
| 普通载荷 | Markdown 正文、位置、天气快照 |
| 加密载荷 | 加密后的上述载荷、算法与 KDF 版本参数、salt、密码封装的密钥、认证所需信息 |

标题按需求保持可见。建议将位置和天气一并加密，减少私密信息旁路泄露；日期等必要索引仍明文。时间点与日记所属的自然日分别存储，避免跨时区后日记变更日期。

索引先只包含必要元数据，可重建；正文按需加载。已锁日记不建立明文全文索引，不向 Spotlight、日志、恢复草稿或缩略图输出正文。用户主动导出明文时提供明确提示。

写入使用同卷临时文件和原子替换。更改加密状态、恢复及格式迁移需要可验证的成功/失败边界，不在失败时丢弃唯一可用副本。

## 单篇加密与 Touch ID

建议使用 CryptoKit 的 AES-GCM 和每篇独立的随机数据密钥；密码经标准、带盐的慢速 KDF 派生封装密钥，再封装数据密钥。KDF 具体算法、成本和格式由 `SEC-001` 验证后固定，参数写入文件以支持迁移。不得直接用密码哈希作为长期加密方案，也不自创密码算法。

密码解锁路径与设备生物识别路径分开：密码保证备份在其他设备仍有解密途径；用户开启 Touch ID 后，本机 Keychain 额外保存受生物识别访问约束的数据密钥。Touch ID 不是日记密码，也不能凭指纹本身重建密钥。

本机 Keychain 密钥不放进日记文件或云备份。更换设备、重新录入指纹、Keychain 失效或签名变化时允许回退日记密码。实际访问控制策略和签名要求必须通过 `SEC-002` 验证，不能先承诺 ad-hoc 构建一定可用。

锁定页面使用合成占位文本呈现模糊效果，不加载真实正文；成功解密后才交给编辑器。切换日记、系统锁屏与退出时清理会话中的正文引用、预览和撤销记录；不宣称 Swift 对象能保证物理内存安全擦除。

为一篇曾以明文保存过的日记开启加密，不能抹去已经存在的 Time Machine、云盘历史版本或旧导出。设计中明确这一边界；不自动删除用户的既有备份。

## iCloud：先做可恢复的备份

主数据留在本地库目录，备份目录由系统目录选择器授权，`BackupDirectory` 保存带 `.withSecurityScope` 的授权书签；书签在应用重开时重新解析，目录被移动或权限被撤销时进入可重试状态，不把授权成功当作云端连接。

每次备份生成不可变快照：`备份根/MacDiarySnapshots/snapshot-<UTC 时间>-<UUID8>/` 内含 `Entries/`、`Trash/`、`manifest.json` 与 `COMPLETE`。先写同卷 `.pending-<UUID>`，所有容器、清单和完成标记落盘后再原子改名；清单只记录相对路径、UUID、是否加密、schemaVersion、字节数与 SHA-256，不含标题或正文。备份前对库目录的 `.writer.lock` 取排他锁，写入进行中返回可重试的 `libraryBusy`；只保留最近 5 个带完成标记的完整快照。已加密日记始终按密文原样复制，普通日记按其原有状态备份，废纸篓一并纳入。

恢复只接受通过清单、`COMPLETE`、精确文件集合与逐文件校验的快照；先写 `.restore-<UUID>` 暂存目录，再逐文件移动到用户选择的隔离目录（日记文件直接位于该目录，废纸篓为其中的 `Trash/`），失败回滚。目标已有日记文件、废纸篓非空、半成品、损坏或清单外文件时拒绝；恢复保留 UUID、密文与 schemaVersion 1...3。多设备双向同步不在此流程内。

手动“立即备份”与保存后 20 秒防抖自动快照并存；目录不可用、库忙或 IO 失败只影响备份状态，不阻塞写作。状态区分：未选择目录 → 正在写入 → 已写入备份目录（本地成功）→ 等待云盘上传 → 系统确认已上传。`BackupCloudInspector` 只在 iCloud 目录且所有文件 `ubiquitousItemIsUploaded` 为真时返回 `uploaded`；普通目录固定 `localOnly`，无法取得证据时为 `unknown`。本地写成功绝不显示为云端完成，也不把普通目录显示为 iCloud 已连接。2026-11-17 在真实 iCloud Drive 目录实测：本地写入、清单校验与隔离恢复通过；系统仅报告 `waitingForUpload`，随后 `brctl status` 显示上传错误 `CKErrorDomain:25` / `Error uploading asset: Quota exceeded`，应用没有显示 `uploaded`。2026-11-18 补齐应用面板路径：用剪贴板路径 + `⌘⇧G` 导航 `NSOpenPanel`，方向键选中目录后通过 AX 按钮授权；面板创建两条快照并显示“等待 iCloud 上传”；退出重开后书签仍解析；目录改名后显示“备份目录不可用，请重新选择目录后再试”，期间编辑器保存成功；恢复目录名后再次快照成功；面板选择隔离空目录恢复并二次确认，恢复 2 活跃 + 1 废纸篓、逐文件 SHA-256 与清单一致，非空目标被拒绝。普通目录在验证模式返回 `localOnly`。真实上传仍被配额阻断，`uploaded` 未验收。

专属 iCloud 容器/CloudKit 是另一条路线，需要评估开发者账号、entitlements、容器与分发签名。本机初步检查只有 Command Line Tools，未发现有效代码签名身份；这是环境现状，不表示用户没有开发者账号。

## 定位、地图与天气

- Core Location 仅响应用户动作或已明确开启的单次采集；处理权限拒绝、超时和陈旧结果，任务结束停止定位。
- Mac 的定位精度受系统与网络环境影响；保存可用的精度和时间，不承诺 GPS 级精度。
- MapKit 提供地图手动选点；自动位置与手选位置使用同一种坐标模型，并记录来源。
- 坐标与显示地名分别保存；逆地理编码失败时可保留有效坐标，地图提供方与坐标转换问题在实机验证，不盲目手工偏移。
- 天气按确认地点请求，缓存当前快照；位置改变时取消旧请求并校验返回结果的归属。
- Open-Meteo 是非商业原型候选；使用其接口会向服务商发送查询坐标，开启天气功能前在产品内说明。日记正文不发送给天气服务商。
- 网络失败、限流、超时、地图不可用均不阻塞写作；保留真实状态与重试入口。

### GEO-001 位置模型与单次定位（2026-11-17）

位置作为 `DiaryPayload` 的可选字段，与坐标一起保存采集时间、精度、来源和可选地名；私密日记的位置位于加密载荷内。只有 Markdown 的容器保持 `schemaVersion = 1`，带位置的容器写为 2，带天气快照的容器写为 3；旧版构建遇到更高版本会保留原文件，避免静默丢弃位置或天气。

Core 定义 `DiaryLocation`、`DiaryLocationProviding` 与请求错误；Platform 的 `SystemLocationProvider` 用一次 `requestLocation()`，把未授权 / 受限 / 超时 / 陈旧结果映射为明确错误，并在每个结束路径停止定位。授权等待（30 秒）与定位等待（20 秒）分开计时，避免用户读授权弹窗的时间占用定位预算。State 只在解锁会话中绑定或清除位置，失败不修改草稿；UI 在日记操作菜单提供“获取当前位置 / 清除位置”，页脚显示已保存地点。

2026-11-17 实机验收通过：允许权限后一次请求在 29 ms 内拿到定位并立即停止；拒绝路径提示后可继续写作、不保存虚构位置；首次尝试曾因 hardened runtime 缺少 `com.apple.security.personal-information.location` 而不弹授权窗并超时，签名脚本已补该 entitlement（profile 无需新增授权项）。精确时间、精度与日志证据见 [location-20261117.json](validation/location-20261117.json)。

### GEO-002 地图选点（2026-11-17）

`LocationMapPicker` 只在 sheet 展示时创建地图，关闭即释放。macOS 的 SwiftUI `Map` 会吞掉点击手势，且拖动时 `onMapCameraChange` 不回调，因此改用 `MKMapView` 的 `NSViewRepresentable` 包装：`mapViewDidChangeVisibleRegion` 持续把地图中心写入选点，`NSClickGestureRecognizer` 支持点击回中，中心准星叠加在地图上。确认后写入 `source = manual`、精度 0 的坐标；取消不修改日记。地图移动 / 点击、取消与确认已实机通过。

地名由 Platform 的 `SystemPlaceNameProvider` 逆地理编码补齐：macOS 26 及以上使用 `MKReverseGeocodingRequest`，否则回退到 `CLGeocoder`；成功时写入可选 `label`，失败返回 `nil`，界面继续显示坐标。地名结果按点快照匹配，移动选点后旧地名不能覆盖新点。地图搜索（`MKLocalSearch`）未加入：当前功能不依赖它，若后续加入，只在地图 sheet 打开时按需请求，结果不写入正文或索引。

### WEA-001 天气快照（2026-11-17）

天气作为 `DiaryPayload.weather` 的可选快照，与位置绑定，字段包括温度、体感温度、WMO 天气码、风速、`fetchedAt`、来源与时区。`schemaVersion = 3` 才允许带天气；位置仍在 v2 级别。私密日记的天气与坐标、地名一起在加密载荷内，锁定后会话清空。

Platform 的 `OpenMeteoWeatherProvider` 只按确认坐标请求 Open-Meteo 当前天气，不在后台轮询；12 秒请求超时，429 映射为限流，网络错误映射为离线/超时。State 的 `DiarySession+Weather` 负责刷新与提交：切换地点先清除旧天气并让在途旧结果失效，过去日期不发起请求；失败只更新状态文字，不改正文、不写虚构快照，日记继续可编辑。Workspace 在设点后按“地名 → 天气”顺序做一次 enrichment，并用弱引用会话防止切换日记后串写。

2026-11-17 实机验收：地图确认后页脚显示“上海市”，随后天气请求第一次遇到真实网络超时，显示“天气请求超时，日记仍可继续写。”且容器未写入天气；重试成功保存 14.4°C、WMO 3、`source = Open-Meteo` 的快照，容器升为 `schemaVersion 3`。过去日期菜单项保持禁用。截图与时间戳记录见 [weather-20261117.json](validation/weather-20261117.json)。

| ADR-014 | 保存失败保留草稿并阻止关闭，冲突不覆盖 | M2 已采用 | 进程锁 + expected revision；窗口及应用退出先 flush，不自动丢弃修改 |
| ADR-015 | 库内废纸篓、排他原子移动和原样恢复 | M2 已采用 | 不改变 v1 容器与密文；同 ID 目标或过期 revision 不覆盖，重开恢复已验证 |
| ADR-016 | 仅按公开标题和记录自然日筛选 | M2 已采用 | 不建立正文摘要或明文搜索索引；按日分组，不根据设备时区修改归属日 |
| ADR-017 | 解锁后显式导出新 Markdown 文件 | M2 已采用 | 保存面板提示未加密正文；直接创建用户选定文件，不生成明文临时缓存或覆盖旧文件 |
| ADR-018 | 用惰性原生控件替代侧栏 OutlineList | 0.4 已采用 | 捕获行高递归调用栈，固定行高无效；替代后千篇启动回归无重入警告，保留键盘与辅助功能 |
| ADR-019 | 编辑器身份校验和显式移除清理 | 0.4 已采用 | 旧回调不能写入新会话；保留旧原生视图测试正文、委托、撤销和组合输入清理 |
| ADR-020 | 密码请求固定到原会话与操作 | 0.4 已采用 | 拒绝过期面板，取消解锁使计算结果失效，输入不持久化；验证和失败重试独立测试 |
| ADR-021 | 位置为 payload 可选字段并引入 `schemaVersion 2` | 2026-11-17 采用 | 旧版遇到 v2 保留文件而非覆盖，避免静默丢弃位置；只含 Markdown 的 v1 容器继续合法 |
| ADR-022 | 地图选点用 `MKMapView` 包装而非 SwiftUI `Map` | 2026-11-17 采用 | macOS 上 SwiftUI `Map` 不回报拖动与点击，实测坐标不更新；`MKMapView` 的原地代理回调与点击手势可验证，地图仍按需创建 |
| ADR-023 | hardened runtime 应用显式声明定位 entitlement | 2026-11-17 采用 | 缺 `com.apple.security.personal-information.location` 时 locationd 不发送授权提示，请求只能超时；该 entitlement 不需要 profile 新增授权项，重新签名并严格验签即可 |
| ADR-024 | 天气快照写入 `DiaryPayload` 并引入 `schemaVersion 3`；地名只写可选 `label` | 2026-11-17 采用 | 天气与位置同属一篇日记的私密上下文，放进加密载荷可避免旁路泄露；失败不写快照，状态只在会话与界面显示；地名失败保留坐标显示，不阻塞写作 |
| ADR-025 | 备份用不可变快照目录 + 清单 + 完成标记，先 pending 后原子改名 | 2026-11-17 采用 | 快照包含 Entries、Trash、加密容器与 schemaVersion 1...3；清单不含标题正文；恢复目标为隔离的库目录语义（文件 + Trash），先校验再写暂存目录，失败回滚 |
| ADR-026 | 本地写入与云端上传状态分离，普通目录固定 localOnly | 2026-11-17 采用 | 只有 iCloud 目录且系统报告所有文件已上传才显示 uploaded；本地成功不冒充云端完成，避免异步云盘状态误导 |


## 风险与应对

| 风险 | 影响 | 必须完成的验证 |
| --- | --- | --- |
| 编辑器 pre-1.0 / 中文输入与撤销错误 | 写作体验与数据完整性 | 固定版本，中文长文、富文本粘贴、撤销、跨日记切换回归 |
| 密码与密钥恢复设计不清 | 备份无法恢复或单篇数据丢失 | 在另一隔离环境仅凭备份与密码恢复；记录密码丢失边界 |
| 本机签名或 Keychain 条件限制 | Touch ID 功能无法使用 | 用计划中的构建方式进行真实设备验证，失败原因可追踪 |
| 云盘异步上传 / 断网 / 空间不足 | 备份状态误报、半成品快照 | 合成目录与真实 iCloud 目录的完成标记、逐文件校验、隔离恢复、面板恢复与 4 类拒绝路径已通过；目录撤销后的面板重试与本地写作已验证；真实 iCloud 因配额阻断上传，应用保持 `waitingForUpload`；断网未单独实测 |
| 全文索引或缓存泄露 | 锁定后仍可读正文 | 检查磁盘、索引、辅助功能、预览、撤销记录和新备份 |
| 地图与天气联网不稳定 | 位置/天气不可用 | 已完成真实定位、地图选点与一次天气超时→重试的实机验证；限流与切换地点实机仍未测，降级为坐标显示与可重试状态 |
| 性能预算不适合最终方案 | 失去轻量目标 | Release 基准；先减少依赖和常驻视图，再记录必要取舍 |

## 0.5 Touch ID 功能链路

Core 的 DiaryBiometricAccess 定义密钥存取与取消接口；Platform 用 Data Protection Keychain 和 LAContext 实现，State 使用取回的数据密钥调用原有 AES-GCM 解密。取消与锁定共用解锁代次保护；认证上下文先在主线程注册，再把阻塞 Keychain 调用放到后台，锁定可取消当前请求。UI 对原会话身份校验后发起认证，始终保留密码路径。

缓存只在用户显式启用时写入，日记容器不增加设备字段。签名能力检查用于准确说明可用性，真正授权仍由 macOS Keychain 执行。签名入口从用户提供的 profile 生成 App ID / Team / 允许的私有组声明，不虚构 Team；实际签名与指纹仍需资产和人工验证。见 [TOUCHID_VALIDATION.md](TOUCHID_VALIDATION.md)。
